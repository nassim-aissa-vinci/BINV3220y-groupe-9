Du composant React à SQLite : afficher les offres

Parcours de la requête GET /offers, responsabilités des couches et fichiers à prévoir pour ajouter un filtre par période.

Architecture en bref

Gesta est une application en npm workspaces composée d'un frontend React/TypeScript avec Vite et d'une API Express/TypeScript avec SQLite. Le frontend organise l'affichage autour des pages, hooks, services, modèles et composants. Le backend sépare HTTP (contrôleurs), règles métier (services), accès SQL (repositories) et conversion des données (mappers). createApp assemble les dépendances; la même application peut ainsi être testée avec une base SQLite en mémoire.

Parcours complet d'une liste

  1. 1

    Route et session côté React

    App appelle useAuth, puis n'affiche la route /offres que si l'utilisateur est connecté et que canListOffers l'autorise. La page reçoit l'utilisateur, le jeton et le rappel de déconnexion en cas de session expirée.

    • frontend/src/App.tsx
    • frontend/src/hooks/useAuth.ts
    • frontend/src/utils/permissions.ts
  2. 2

    Page et état de chargement

    OffersPage appelle useOffers(token, onUnauthorized). Elle rend l'état d'erreur, de chargement, la liste vide ou le nombre de résultats et le tableau.

    • frontend/src/pages/OffersPage.tsx
    • frontend/src/hooks/useOffers.ts
  3. 3

    Appel HTTP et proxy Vite

    Le hook lance getOffers avec un AbortSignal. Le service envoie le jeton directement dans l'en-tête Authorization et appelle /api/offers. En développement, Vite transmet la requête à l'API (port API_PORT, 3000 par défaut) en supprimant le préfixe /api.

    • frontend/src/services/offers.service.ts
    • frontend/src/utils/api.ts
    • frontend/vite.config.ts
  4. 4

    Initialisation de l'API et middleware

    main.ts charge la configuration, initialise SQLite et démarre Express. app.ts monte la route des offres derrière authenticate. L'identité du jeton est vérifiée, puis le compte, ses rôles et ses entreprises sont relus en base; authorize refuse l'accès des profils non autorisés (403).

    • backend/src/main.ts
    • backend/src/app.ts
    • backend/src/middlewares/authenticate.ts
    • backend/src/middlewares/authorize.ts
  5. 5

    Contrôleur et visibilité métier

    Le contrôleur GET /offers récupère l'utilisateur authentifié, appelle le service puis convertit les résultats en DTO JSON. Le service applique les règles par profil : toutes les offres pour l'administrateur, les offres publiées pour l'étudiant, celles déposées par le contact déposant; un contact sans rôle de déposant reçoit 403.

    • backend/src/controllers/offers.controller.ts
    • backend/src/services/offers.service.ts
    • backend/src/services/permissions.ts
  6. 6

    SQL, jointures et conversion

    Le repository sélectionne les offres en joignant les entreprises, années académiques et périodes. Il applique les filtres métier transmis par le service, puis trie par année académique décroissante et date de création décroissante. Le mapper convertit la ligne SQL (OfferDbo) en objet métier, puis en DTO limité aux champs exposés par l'API.

    • backend/src/repositories/offers.repository.ts
    • backend/src/mappers/offer.mapper.ts
    • backend/src/models/offer.ts
    • backend/src/db/migrations/001_initial.sql
  7. 7

    Validation de la réponse et rendu

    Le service frontend vérifie le statut HTTP et valide le JSON avec isOfferList. Le hook alimente l'état de la page ou déclenche la déconnexion sur 401. Enfin, OfferTable affiche titre, entreprise, année, période et statut; les codes sont traduits par les libellés frontend.

    • frontend/src/utils/guards.ts
    • frontend/src/models/offer.ts
    • frontend/src/components/OfferTable.tsx
    • frontend/src/utils/labels.ts

Ajouter un filtre par période

L'API renvoie déjà le code de période (P1, P2 ou OTHER) pour chaque offre, et le repository joint déjà la table periods. Pour filtrer côté serveur sans contourner les droits existants, transmettre un code facultatif dans la query, par exemple GET /offers?period=P2. La visibilité du profil et la période doivent se combiner par intersection.

Fichier Évolution à prévoir
frontend/src/pages/OffersPage.tsx Ajouter le contrôle de période et gérer la valeur sélectionnée; transmettre la sélection au hook.
frontend/src/hooks/useOffers.ts Accepter la période sélectionnée, déclencher le chargement lorsque celle-ci change et conserver les états de chargement/erreur.
frontend/src/services/offers.service.ts Ajouter la période à l'URL comme paramètre de query (et omettre le paramètre lorsqu'aucun filtre n'est sélectionné).
backend/src/controllers/offers.controller.ts Lire et valider le paramètre unique period; rejeter une valeur inconnue avec l'erreur de requête standard (400), puis transmettre le filtre au service.
backend/src/services/offers.service.ts Combiner le filtre choisi avec les contraintes de visibilité du profil; ne jamais remplacer le filtre de droits par la sélection utilisateur.
backend/src/repositories/offers.repository.ts Étendre OfferFilter et les paramètres SQL; filtrer par le code de période joint (par exemple p.code).
backend/tests/offers.test.ts Tester les périodes valides, les périodes sans résultat et la combinaison du filtre avec les droits administrateur, étudiant et déposant; couvrir les paramètres invalides au niveau API.
frontend/tests/OffersPage.test.tsx Vérifier le contrôle, l'URL ou le résultat filtré, ainsi que les états vides et le changement de période.
backend/API.md Documenter le paramètre facultatif, les codes admis, son comportement et la réponse 400.
Éléments déjà disponibles : PeriodCode et PERIOD_CODES existent dans les modèles, les type guards valident déjà la période retournée, et SQLite associe chaque offre à une période via les clés étrangères. Aucun nouveau champ de réponse, changement de schéma ou migration n'est nécessaire pour un filtre sur P1, P2 et OTHER. OfferTable peut rester inchangé si le filtre est placé dans la page.
